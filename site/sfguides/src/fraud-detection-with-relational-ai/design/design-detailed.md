## 1. Purpose and Positioning

**One-liner:** Detect coordinated payment fraud that is invisible when each customer, account, or transaction is examined on its own — and hand investigators a ranked, explainable list of suspicious rings.

**Why this quickstart:** Existing RAI quickstarts in the repo (`community-detection-using-relationalai`, `discovering-the-social-graph-...`, `kgqa-using-relationalai`) show single algorithms on retail/social data. None covers financial crime, none combines several reasoners, and most use the pre-v1 RAI Python API. This guide fills that gap with a realistic end-to-end fraud workflow on the current PyRel v1 API (`relationalai.semantics`).

**Scope (MVP):** Payment fraud / mule networks. Claims fraud is mentioned as an extension, not built.

**Audience:** Data scientists, fraud analytics engineers, Snowflake SEs/partners. Assumes basic SQL and Python; no graph theory required.

**Duration:** ~60 minutes.

## 2. Learning Outcomes

### What You'll Learn
- Model customers, accounts, devices, identifiers, and transactions as a heterogeneous knowledge graph over Snowflake tables
- Derive a person-to-person "shared identifier" graph with business rules
- Detect fraud rings with community detection (e.g., Louvain / WCC)
- Find suspicious motifs: fan-in/fan-out, circular flows, pass-through accounts
- Propagate risk from confirmed fraud cases through 2nd/3rd-degree connections
- Score similarity of new communities to known fraud rings
- Write investigator-ready results (ring, members, evidence paths, at-risk value) back to Snowflake tables

### What You'll Build
- A synthetic payments dataset in Snowflake
- A RelationalAI model (Python notebook) with fraud rules and graph analytics
- Output tables: `FRAUD_RINGS`, `RING_MEMBERS`, `RING_EVIDENCE`, `ENTITY_RISK`
- (Optional) A Streamlit-in-Snowflake investigator view

### What You'll Need
- Snowflake account (region where RAI Native App is available) with ACCOUNTADMIN or privileges to install Native Apps
- RelationalAI Native App installed from Marketplace
- Snowflake Notebook (Container Runtime) **or** local Python 3.10/3.11 + `relationalai` package
- Assets from this guide's GitHub repo (data generator, notebook, setup SQL)

## 3. Narrative / Storyline

Fictional bank "Frosty Bank" sees chargebacks rising, yet its per-transaction rules model flags nothing unusual. Investigators have **5 confirmed fraud cases**. The guide answers, in order:

1. Who is secretly connected to whom? (shared identifiers)
2. Which groups form rings? (communities)
3. Which rings behave like mule networks? (motifs)
4. Who is near confirmed fraud? (risk propagation)
5. Which new rings look like known ones? (similarity)
6. What should an investigator look at first, and why? (ranked, explained output)

Each section ends with a concrete "aha" result visible in a query output.

## 5. Data Design (synthetic)

Generated by a deterministic Python script (seeded) and loaded via SQL, so results are reproducible and the guide can quote exact numbers.

| Table | Key columns | Approx rows |
|---|---|---|
| `CUSTOMERS` | customer_id, name, dob, signup_date, kyc_level | 5,000 |
| `ACCOUNTS` | account_id, customer_id, open_date, type, balance | 6,500 |
| `DEVICES` | device_id, device_fingerprint, os | 4,000 |
| `CUSTOMER_IDENTIFIERS` | customer_id, id_type (PHONE/EMAIL/ADDRESS/DEVICE/SSN_HASH/IBAN), id_value | 25,000 |
| `MERCHANTS` | merchant_id, name, mcc, country | 300 |
| `TRANSACTIONS` | txn_id, src_account, dst_account \| merchant_id, amount, ts, channel | 200,000 |
| `CONFIRMED_FRAUD` | customer_id, case_id, confirmed_date, loss_amount | 5 seeds |

**Planted patterns** (ground truth kept in `_GROUND_TRUTH` for validation, not exposed to the model):
- 6 fraud rings of 4–15 members sharing devices/phones/addresses
- 3 mule chains (A→B→C→D pass-through within hours, near-zero residual balance)
- 2 circular flows (A→B→C→A)
- 2 fan-in collectors (≥20 senders → 1 account in 48h) and fan-out distributors
- Benign noise: families sharing an address, shared corporate devices (to show false positives and why multi-signal evidence matters)

Open question: generate in-notebook (simpler) vs. ship CSVs on a stage (faster, more robust)? **Proposal:** ship CSVs + setup SQL; keep generator script in repo for transparency.

## 6. Model Design (PyRel v1)

> Exact syntax will be authored and validated with the `rai-pyrel` / `rai-ontology` / `rai-graph-analysis` skills against the current release. Snippets below are illustrative intent, not final code.

### 6.1 Concepts
`Customer`, `Account`, `Device`, `Identifier` (subtyped by kind), `Merchant`, `Transaction`, `FraudCase`.

### 6.2 Relationships
- `Customer owns Account`, `Customer uses Device`, `Customer has Identifier`
- `Transaction from Account to Account|Merchant` with amount, ts
- `Customer is_confirmed_in FraudCase`

### 6.3 Derived rules
| Rule | Logic |
|---|---|
| `shares_identifier(c1, c2, kind)` | two distinct customers with same identifier value; weight by kind (device/SSN high, address low) |
| `is_pass_through(account)` | inflow ≈ outflow within 24h, residual < 5% |
| `is_fan_in(account)` / `is_fan_out` | ≥N distinct counterparties in window |
| `in_cycle(account)` | part of a transaction cycle length 3–5 |
| `young_account` | opened < 30 days before first suspicious txn |

### 6.4 Graph analytics
| Step | Graph | Algorithm | Output |
|---|---|---|---|
| Ring detection | Customer–Customer (weighted shared identifiers) | Louvain (fallback: WCC) | `community_id` |
| Key players | Same | Degree / PageRank / betweenness | `centrality` per member |
| Flow motifs | Account–Account (transactions) | Cycle/path enumeration, reachability | evidence paths |
| Proximity to fraud | Combined | Shortest path / reachable within 3 hops from `FraudCase` customers | `hops_to_fraud` |
| Similarity | Community feature vectors or Jaccard on members' neighbourhoods | Jaccard / cosine vs. known-fraud communities | `similarity_to_known` |

### 6.5 Risk propagation
Transparent rule-based score (not a black box):

```
entity_risk = max over confirmed seeds s of  base(s) * decay^hops(s, entity) * edge_weight
ring_score  = w1*avg_member_risk + w2*motif_count + w3*similarity_to_known
              + w4*log(at_risk_value)
```
Decay 0.5, weights exposed as notebook parameters so readers can tune them. Optional extension: GNN via `rai-predictive-*` (out of scope for MVP).

### 6.6 Explanations
For each ring: top shared identifiers, strongest path to a confirmed fraud seed (`A —device→ B —txn $4.2k→ C (case F-002)`), motifs present, total at-risk value (balances + 30-day inflows of members).

|---|---|
| `FRAUD_RINGS` | ring_id, member_count, ring_score, similarity_to_known, motif_flags, at_risk_value, rank |
| `RING_MEMBERS` | ring_id, customer_id, centrality, entity_risk, hops_to_fraud, role (hub/mule/peripheral) |

## 12. Risks and Open Questions
1. **API currency:** PyRel v1 graph API (algorithm names, weighted Louvain, cycle enumeration) must be verified; cycle detection may need a rule-based fallback.
2. **Snowflake Notebook vs. local Jupyter:** recommend Snowflake Notebook (Container Runtime) — confirm RAI support and package install path.
3. **Region availability** of the RAI Native App — state explicitly.
4. **Companion repo** ownership: Snowflake-Labs vs. RelationalAI `rai-samples`?
5. **Co-authorship / review** with RelationalAI team?
6. **Optional Streamlit section** — include in v1 or defer?
7. **Similarity method:** Jaccard on neighbourhoods (simple) vs. structural embedding (richer, harder to explain). Proposal: Jaccard.
